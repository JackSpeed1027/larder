# 20 注释与复杂机制讲解规范

执行对象：每一位生成或修改代码、SQL、配置和脚本的Agent。用户需要通过项目理解机制，注释是交付要求。代码简洁不等于没有解释；注释不能替代清楚命名、合理分层或测试。

## 1. 每次生成都要有的简单注释

| 产物 | 必须注释的内容 |
|---|---|
| Java类/接口/enum | 一两句说明职责、模块边界；enum说明状态/码用途 |
| Java公开方法、关键私有方法 | 输入/输出含义、主要副作用；有事务/异常/幂等条件必须写 |
| Request/Response/Command字段 | 业务含义、单位、来源、可空语义、版本/幂等用途；生成模型在schema description写，再由生成器带入 |
| Python模块/公开函数/类 | docstring写职责；I/O、并发、取消或恢复函数写副作用与失败条件 |
| TS页面/共享组件/非显然hook | 页面职责、props关键语义、状态来源；SSE/异步竞争/焦点等写关键原因 |
| SQL表/字段 | 每张表与每个字段都写COMMENT；关键唯一约束/索引旁写目的 |
| migration | 文件头写版本目的、前置、数据影响、不可逆风险；不要写清库回滚 |
| 配置项 | 含义、单位、默认/上限、生效范围、敏感性；ENV示例只占位，不写秘密 |
| 脚本/CI | 目的、运行前提、会写哪里、失败退出；危险环境检查必须清楚 |

不要求给每行赋值、每个getter写“设置xxx”类机械注释；简单内部局部变量可用清楚名字表达。注释写“为什么与边界”，不是换一种语言重复代码。中文为解释默认语言，字段/协议名保持英文准确。不要写作者广告、虚假日期、营销式“高性能线程安全”。

## 2. 复杂逻辑必须有的六项说明

紧邻实现写完整块注释，至少包含：**业务问题；关键不变量；执行顺序/线性化点；失败与恢复；不能保证什么；对应测试/设计编号**。复杂到一屏以上时在docs/mechanisms创建深入说明，代码保留摘要和可点击/可定位相对引用，不能只留“详见文档”而无关键约束。

以下位置属于必需详细注释：Outbox确认与重投；Inbox接管后ack；租约/fencing/epoch；Redis锁/看门狗；索引任务完成与CAS发布；JSONL fsync/段恢复/checkpoint提交；UNKNOWN外部调用；审批版本/hash/幂等；memory撤销授权竞争；预算预留/差额结算；context原子提交；复习幂等；前端SSE乱序/翻卡焦点与评分。

## 3. Redisson锁与看门狗示范

本项目的最终提交正确性仍由MySQL条件保证。Redisson若引入，先在L03实验比较“热点缓存重建单飞”场景，满足收益和资源约束后作为V07缓存层可选实现；不自动增加到业务任务的最终锁。使用前冻结实际Redisson版本与依赖兼容，按官方文档和源码核对重载及续租行为。

[Redisson官方锁说明](https://redisson.pro/docs/data-and-services/locks-and-synchronizers/index.html)和[配置说明](https://redisson.pro/docs/configuration/)说明：未显式指定租期的锁可由watchdog续期；默认lockWatchdogTimeout为30000ms，可配置；释放受持有线程约束。具体续期调度细节以锁定版本为准，不写死“任何情况下每10秒一定成功续期”。

下面是**应写在锁获取附近的注释范式**，不是当前已实现的业务代码：

```java
/*
 * 目的：合并同一缓存key的并发重建，减少对下游的重复查询。
 * 这把锁只优化重复工作，不决定用户数据是否允许发布。
 *
 * tryLock(waitTime, unit)未指定leaseTime，使用本项目锁定版本的watchdog续租。
 * 不要误改成tryLock(waitTime, leaseTime, unit)后仍声称会自动续租。
 * waitTime限制等待获取锁的时间，不是业务执行期限；业务查询另有总deadline。
 *
 * GC长暂停、网络分区、Redis故障都可能导致续期失败并失去锁。
 * 因此缓存写入必须携带内容/profile版本，业务提交另检查DB leaseToken/epoch。
 * 锁释放必须在同一持有线程的finally中；异步切线程不能沿用普通RLock示例。
 * 未拿到锁采用已有缓存或有界等待，不能无限阻塞用户请求。
 *
 * 参见 docs/02 缓存边界、L03：续期成功、客户端退出、网络隔离、迟到旧写。
 */
boolean acquired = lock.tryLock(0, TimeUnit.SECONDS);
```

释放处也需要解释：`isLocked()`只说明某人持有，不能证明当前线程拥有；`isHeldByCurrentThread()`用于当前线程归属，但检查与unlock间仍可能失去租约。不能在finally不区分情况地forceUnlock，否则可能破坏他人锁。对锁已失效/Redis不可达的释放失败按本场景策略记录并保留原始业务异常，避免finally异常覆盖真正原因；是否允许业务结果继续返回取决于这个锁只优化缓存的边界。不能将相同处理直接复制到审批或数据库发布。

详细讲解文件必须画出A获取→续期→A暂停/断网→TTL过期→B获取→A恢复的时间线，说明为什么watchdog不等于防止迟到写，以及DB fencing或版本化缓存key如何阻止过时结果产生错误效果。实验报告列真实配置、进程/网络注入、观测结果，不能把“开了watchdog”当测试。

## 4. DB fencing注释范式

```java
/*
 * 该条件更新是候选正文发布的最后一道保护。
 * leaseToken拒绝已被接管的旧worker；processingEpoch拒绝用户新一次重抓之前的结果。
 * 两者解决不同竞争，不能只保留其中一个，也不能用Redis锁代替。
 * 对象已在事务外按hash验证；当前事务内复核取消、删除、目标归属和租约期限。
 * affectedRows == 0表示执行权或目标版本已变化，必须抛出明确陈旧状态，不能返回成功。
 * 事务失败可能留下未引用对象，但不能留下指向未验证对象的有效revision。
 * 验证：A05旧worker迟到、A06旧epoch、A07取消/删除竞争。
 */
```

## 5. JSONL / 审批 / 记忆注释必须回答的问题

JSONL：为何先fsync再对外事件？recordHash包括哪些字节、是否排除自身？末行半写为何保留并开新段，中段损坏为何停止？checkpoint文件存在为何不能直接采用？模型请求发出后没有结果为何UNKNOWN而非FAILED？

审批：批准绑定哪些字段？同action重复请求为何返原结果？目标版本变化如何拒绝？效果与APPLIED/result/audit为什么同事务？此保证是否仅限DB内动作？

记忆：撤销和authorize-model-call如何锁同一owner形成顺序？为什么新call不能复用旧context记忆？已经授权在途的请求为什么无法保证撤回？policyEpoch和memoryVersion是否混用？

这些解释写在对应方法/事务附近，并关联A11–A13/A19–A24。不能让读者在十个无关联工具类里拼出核心原理。

## 6. SQL注释标准

表COMMENT写“管理什么事实/权威或投影/是否不可变”；字段COMMENT写业务含义，时间注明UTC或用户本地日，金额注明币种字段，版本字段说明用途，状态列写枚举语义。

```sql
-- 按状态与下次对账时间有界扫描；支持ACK后进程退出仍能继续派发/查询。
KEY ix_job_reconcile (state, next_reconcile_at, id)

-- 示例字段，不作为独立迁移执行：
lease_token BIGINT NOT NULL DEFAULT 0 COMMENT '执行租约代次；接管递增，旧worker提交必须被拒绝'
```

不要把 `row_version` 注释为“版本号”就结束；要区分乐观并发版本、不可变内容版本、索引schema版本、policyEpoch。只写“id=主键”不足以解释跨系统标识，runId/actionId/callId都要写各自用途。DDL上的COMMENT跟随迁移变化，不另维护一份永远过时的Excel字典。

## 7. 注释与代码同步检查

每次改状态/重试/锁/事务/配置默认值，同步对应注释、机制文档和测试。审查时优先找“注释说保证了，代码实际上没检查”的情况。自动检查可提示缺少表/字段COMMENT或公开符号docstring，但注释是否正确必须人工/Agent结合实现审查。

handoff增加 `commentReview`：新增公共符号覆盖、SQL表/字段COMMENT、复杂机制六项说明、对应测试ID、修改后的注释是否仍准确。复杂机制缺少说明不能TASK_LOCAL_PASS；不以测试已绿为由跳过用户学习可读性要求。

## 8. 不做什么

不写逐行翻译和无意义长注释；不让陈旧注释误导；不把watchdog说成永不失锁；不抄锁示例却跨线程unlock；不把注释当测试证据；不在注释/样例中放真实秘密和用户正文。
