# 18 编码风格与公共封装实施规范

执行对象：所有实现Agent。补充09，体现用户要求：代码不冗余、避免为了简短大量使用新特性、返回与传参专业、异常可以表达具体业务含义、合理封装且方便扩展。本文是公共基础slice的实现合同；类名是设计要求，示例不是当前已有生产代码。

## 1. 风格：优先显式与容易调试

Java21是运行基线，不代表必须使用Java21全部语法。默认普通命名类、明确类型、构造器注入、if/for、早返回、命名局部变量。禁用preview；不默认引入虚拟线程、反射式通用CRUD、复杂泛型技巧、泛滥的模式匹配、深层Stream/Optional链。确有并发收益的实验可独立评估，不能为了简历关键词改变核心执行模型。

Stream限于简单filter/map/collect，无副作用，超过3个转换或需要debug复杂分支改为循环/具名函数；不得在stream里发SQL/HTTP。Optional仅适合明确可缺的返回，不当DTO字段或方法参数。异常处理不包成“吞异常返回Optional.empty”。类型清楚时少量var可读，但默认跨层关键变量写完整类型。record不作为默认DTO标准，普通Request/Response类更便于统一验证、序列化和后续演进；如团队统一改用record须评估生成器和验证工具后一次性决策，不能各窗口混用偏好。

Python使用普通函数、dataclass/Pydantic边界模型、显式循环与async/await；不使用动态改类、元类、全局monkey patch或难读的嵌套推导式。TS使用明确组件props和判别联合表达状态；不大量any、类型断言或多层条件类型。语言支持的新特性如果明显降低复杂度且团队可理解，可在局部说明使用理由；不是全面禁用现代语言能力。

命名表达业务，例如 `publishGeneration`、`approveProposal`、`reserveBudget`，不叫 `handleData`、`doBusiness`、`CommonManager`。布尔变量写可判断含义，禁止神秘flag1/flag2；时间/金额命名带含义或单位。注释解释事务边界、失败条件和设计原因，不逐句翻译代码。

## 2. 先划边界，再封装

| 应统一封装 | 不应强行统一 |
|---|---|
| HTTP结果/错误、参数校验、cursor分页、trace、clock | 所有业务都塞进一个BaseService<T> |
| 幂等请求登记、受控重试策略、事务内审计记录 | 无论读写都自动重试的全局拦截器 |
| RunnerClient、ObjectStore、索引客户端、模型Provider | 一个万能Client用字符串区分所有外部服务 |
| CitationRef、版本前置条件、预算金额值对象 | 把完全不同的card/approval/memory聚合共用一张表 |
| 统一UI基础组件/HTTP错误/SSE重连 | 把所有页面变成巨大JSON驱动表单引擎 |
| 纯算法接口如RRF和ReviewScheduler | 每个只有一个实现的内部工具类都套接口+工厂 |

重复两次不必马上抽象：先判断是否同一业务语义、是否会一起变化、边界是否稳定。确属同一规则，即使只有两处也应集中；只是代码形状相似但语义不同则保留分别实现。抽取后调用方应更容易理解，不出现十个布尔配置参数。

## 3. Java 公共包的精确职责

```text
com.larder.common/
  api/         ApiResponse, ApiErrorResponse, CursorPage, FieldViolation
  error/       ErrorCode, CommonErrorCode, BusinessException,
               NotFoundException, StateConflictException,
               AccessDeniedBusinessException, DependencyException
  web/         GlobalExceptionHandler, TraceFilter, PageRequestValidator
  time/        ClockConfig
  json/        JsonCodecConfiguration
  validation/  公共语义校验（不放具体业务规则）
```

幂等、审计、限流、预算有业务/存储依赖，放各自platform/pipeline模块，不塞进common；公共包不得反向引用content/assistant/learning。`common`只存稳定跨模块机制和小值对象。

Java依赖默认不为省几行盲目加库。若采用Lombok，由V01锁定且限制为Getter、明确的constructor等可预测用途；实体/命令禁止@Data自动生成不合适的equals/hashCode/toString；包含秘密的字段禁止自动toString。团队也可统一手写少量样板代码，不能不同Agent各自加入不同生成器。

## 4. 请求、应用命令与返回对象

边界必须独立：HTTP Request DTO → application Command/Query → domain/value → Response DTO。MyBatis PO不直接返回前端；Controller不接受`Map<String,Object>`承载结构固定的业务参数；不让客户端传ownerId、leaseToken、内部state、数据库主键序列等由服务端控制的字段。

例如CreateItemRequest只含kind、url/text/uploadId之一、title、collectionIds、tagIds；身份来自认证上下文；idempotencyKey来自请求头。Bean Validation做长度/格式/必填；跨字段互斥由明确验证器；业务归属、状态和并发版本在application/事务中校验。后端严格拒绝不认识的命令字段，避免传错字段静默丢失。

应用层使用 `CreateItemCommand` 传递已经识别身份的ownerId和规范化请求；超过约4个有独立语义的参数优先命令对象，不新增十参数Service方法。仅两个简单内部参数不机械生成DTO。Query对象和Command对象分开，PATCH区分未提供/null/有值，不能用Java null同时代表“保持原样”和“清空”。

响应对象面向使用场景：ItemListResponse、ItemDetailResponse、RevisionResponse、ApprovalDetailResponse；不创建一个包含所有表字段的万能ItemDto。转换小规模手写assembler，重复且字段多时再统一引入映射器；不能用反射copyProperties掩盖字段遗漏或泄漏。枚举与时间序列化固定，有新增枚举兼容策略。

## 5. 公开Java API成功响应与错误响应

本节明确补充04：**Java面向Web的普通JSON成功响应统一ApiResponse<T>，错误统一ApiErrorResponse**。内部Runner协议继续使用既有机器schema的原始对象；SSE、文件下载和health/metrics按各自协议，不被全局ResponseBodyAdvice无脑套壳。Java内部工具API在冻结OpenAPI时明确指定响应型，不由客户端猜是否有data。

```json
{
  "code": "OK",
  "message": "操作成功",
  "data": {"itemId": "01...", "jobId": "01..."},
  "traceId": "<请求关联标识>"
}
```

HTTP状态仍保留200/201/202，创建后尚在处理用202；不把202映射成“内容已处理完”。`code=OK`是成功语义，不是HTTP状态副本。`message`仅作默认安全显示，程序不解析中文文案做逻辑。没有业务结果用ApiResponse<Void>且data=null，或契约明确204无body；同一路由固定一种。

```json
{
  "code": "APPROVAL_STALE",
  "message": "内容已发生变化，请重新生成修改提议",
  "traceId": "<请求关联标识>",
  "retryable": false,
  "details": {"expectedVersion": 3, "actualVersion": 4}
}
```

此错误必须返回HTTP409。错误对象不塞假data，不返回堆栈/SQL/secret；权限错误details不暴露目标私有字段。成功/错误分别用泛型和固定模型，避免一个巨大Result含十几个仅一半生效的字段。TS/Python客户端按HTTP状态与schema解析，两类模型均由契约生成。

分页`ApiResponse<CursorPage<T>>`的data固定 `items,nextCursor,hasMore`，需要且确实计算总数时才有total；没有准确总数不要填0。limit默认20最大50，不接受前端60。前端不把分页体拆成另一个不兼容PageResult。普通列表用ArrayList/集合，API返回List接口；不暴露数据库分页插件专用类。

## 6. 可复用异常体系

错误码接口供不同业务枚举实现，集中登记唯一字符串及HTTP映射；ErrorCode不是把所有模块业务塞入巨型公共enum。接口概念：`code()`、`httpStatus()`、`defaultMessage()`、`retryable()`。transport状态映射可集中web层registry；domain纯算法不依赖HTTP类型。

`BusinessException`继承RuntimeException，持有ErrorCode、用户可安全显示的描述、白名单details、cause。可提供简短构造器与具名factory，禁止调用方将原始SQLException.getMessage直接作为public message。异常对象不能持有整个请求/正文/Key。日志保留cause用于定位，但面向用户返回映射后的内容。

常用子类只在语义或处理有区别时创建：NotFoundException、StateConflictException、AccessDeniedBusinessException、DependencyException；审批/预算等可使用本模块enum配BusinessException。若某异常需要稳定的额外结构或专门处理，再增加如ApprovalStaleException。**不为100个错误码机械生成100个空子类**，也不用所有场景一个RuntimeException("失败")。

调用示意（样例，类实现由基础slice补齐）：

```java
int affectedRows = approvalMapper.markApplied(
        approvalId, expectedVersion, payloadHash, now);
if (affectedRows != 1) {
    throw new StateConflictException(
            ApprovalErrorCode.APPROVAL_STALE,
            "审批状态或目标内容已变化，请重新生成修改提议");
}
```

这段代码只有在同一事务里已按04检查owner/run/expiry/targetVersions，并且后续业务效果/action_result/audit一起提交时才正确；不能只复制这段CAS就宣称审批安全。描述可针对场景具体化，客户端仍以稳定code分支。

可预期的批量部分成功使用 `BatchResult<Success,Failure>` typed result逐项返回，不为每个可恢复未命中抛异常。正常“没有查询结果”返回空列表/明确Optional，不抛系统异常；写命令目标不存在应返回404。审批失败/预算拒绝等业务异常不能被catch(Exception)转换为默认成功。

## 7. 全局异常处理映射

| 来源 | HTTP/code | 处理 |
|---|---|---|
| 参数不合法/未知字段 | 400 / VALIDATION_FAILED | field violations含字段名与安全描述，不回显密码/整段输入 |
| 未登录/会话过期 | 401 / UNAUTHENTICATED | 同一错误合同，认证filter也走统一writer |
| 权限/CSRF拒绝 | 403 / FORBIDDEN_TARGET或CSRF_REJECTED | 不泄资源存在与私密内容；按端点策略可返回404 |
| 目标不存在 | 404 / NOT_FOUND | 公共安全描述 |
| 幂等body不一致/版本竞争 | 409 / IDEMPOTENCY_CONFLICT或STALE_WRITE | 客户端刷新/查原结果，不能无条件自动重试 |
| 超量/限流 | 413或429 | 字段/限制清楚，429按适用返回Retry-After |
| 外部依赖确定不可用 | 503 / DEPENDENCY_UNAVAILABLE | 仅允许幂等且有预算的受限重试 |
| UNKNOWN外部结果 | 409或已存在run的状态响应 | 以具体接口契约为准，呈NEEDS_DECISION，不能全局自动重试 |
| 未预期异常 | 500 / INTERNAL_ERROR | 完整私有日志关联traceId，用户通用描述，不泄堆栈 |

GlobalExceptionHandler处理MVC异常，Security entry point/access denied handler使用同一个ErrorResponseFactory；Filter链异常不一定进入ControllerAdvice，必须补齐路径。validation、JSON parse、upload limit也有一致错误模型。异步worker异常更新相应job状态与事件，不能套Controller handler解决全部后台错误。

框架机制依据：[Spring MVC异常处理官方说明](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-controller/ann-exceptionhandler.html)。实现时使用项目锁定的Boot4.1对应Spring版本API，不因网页默认版本变化自动升级依赖。

记录原则：在最终处理边界记录一次完整stack，底层不要同一异常重复error再throw造成日志洪水；预期409/400按适当级别记录安全元信息；未知500完整cause。异常catch必须有明确恢复、翻译或资源处理目的；不写空catch，不返回null冒充已处理。

## 8. 灵活性通过扩展点提供

ObjectStore、RunnerClient、ModelProvider、ReviewScheduler、ToolHandler、RetrievalStrategy、Clock是稳定扩展边界。使用构造器注入和配置选择，默认只保留实际需要的实现；新增供应商/卡型/工具时不修改不相关模块。简单业务用具名函数组合，不搭建自己的复杂工作流框架。

错误码、配置项、API和DTO都按显式版本演进；新增实现必须通过共用合同测试。扩展点不是绕过约束的入口：新ToolHandler仍强制scope/审批，新的Provider仍强制预算/UNKNOWN，新ObjectStore仍强制不可变hash，新ReviewScheduler仍必须留schedulerVersion并可重放历史。

## 9. Agent代码审查硬检查

1. 同一规则是否复制多处？是否有无意义的BaseX/Manager/Util大类？
2. 是否为了短代码堆新语法、嵌套lambda、隐藏I/O或过度泛型？
3. DTO/Command/PO是否分离？字段来源与所有权校验是否清楚？
4. 成功/错误响应及HTTP状态是否一致？分页是否真有总数？
5. 异常是否有稳定code、具体安全描述、正确重试语义？cause是否保留？
6. 是否吞异常、返回默认成功、catch里重试非幂等调用、日志泄密？
7. 公共封装是否使业务代码更清楚？增加一个卡型/工具需要改几处，是否都有明确理由？
8. 是否用真实并发/故障验证关键边界，且没有只断言message字符串的脆弱测试？

## 10. 不做什么

不把专业等同于层数多；不把灵活等同于任意Map和万能JSON；不把复用等同于继承所有Service；不以新语法炫技；不强行所有失败HTTP200；不为每个字段创建类；不以异常封装掩盖事务、权限和未知外部效果。
