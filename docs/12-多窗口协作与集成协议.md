# 12 多窗口协作与集成协议

执行对象：所有编码Agent。本文是协作控制面协议，与产品内部的worker lease、MQ任务和run状态机没有字段复用关系。协调台记录保存于未来应用仓库的 `coordination/`，不存用户凭据、私密正文或模型隐藏思维。

## 1. 单一协调者与写权限

| 角色 | 负责 | 默认不可写 |
|---|---|---|
| C / Coordinator | 盘点、分解、派工、全局任务状态、契约冻结、共享文件、集成、门禁报告 | 用户历史、真实数据、未授权发布 |
| B / Backend | 被分配的Java业务包/mapper/测试；提出SQL迁移草案 | 未分配模块、root构建、公共契约、他人迁移 |
| R / Runner | 被分配的Python子包/测试，HTTP与journal实现 | Java数据库、MQ直接访问、共享runtime任意改写 |
| W / Web | 被分配feature页面/测试；严格使用设计系统 | 自创新token/路由/HTTP格式、改后端契约自救 |
| Q / QA | 契约、故障、场景、浏览器验证、独立证据审阅 | 为让测试变绿而改变业务规则、伪造证据 |

C可明确临时授予一个worker共享文件的独占所有权，须记录精确路径、有效任务、释放条件；此时C自己也不同时改。工单里写“完成某功能”并不赋予整个仓库修改权。已授权范围内继续定位/修复，不为每次正常编辑询问用户。

## 2. 开工所需派工单

每个worker收到以下非空字段才进入写阶段。缺项先只读检查，向C报告缺少字段；不让用户反复解释架构。

```json
{
  "assignmentId": "R3-V08-T03-BE-001",
  "taskId": "V08-T03",
  "sliceId": "V08-T03.BE",
  "ownerId": "window-backend-1",
  "workspace": "<本窗口独立工作目录的绝对路径>",
  "baseSnapshot": "<基线manifest的sha256>",
  "contractRev": "<冻结manifest的sha256>",
  "designRev": "<前端token/页面规格manifest的sha256或经解释的N/A>",
  "dependsOnEvidence": ["<已集成前置任务报告绝对路径>"],
  "allowedPaths": ["backend/src/main/java/com/larder/assistant/approval/", "backend/src/test/java/com/larder/assistant/approval/"],
  "exclusiveResources": ["module:approval"],
  "acceptanceIds": ["A19", "A20"],
  "evidenceDirectory": "<reports/V08-T03/唯一runId的绝对路径>",
  "integrationOwner": "window-coordinator"
}
```

所有带尖括号的值必须在派工前替换；不是示例路径就能直接执行。WORKSPACE必须在明确授权工作区内。C记录role、ownerId、heartbeat、锁清单、开始时间、预期2–6h时长。C用单一台账维护认领，不要求worker同时写同一tasks.json。

## 3. 状态机

`PLANNED → IN_PROGRESS → READY_FOR_INTEGRATION → VERIFYING → DONE`；任何非DONE可进入BLOCKED；阻塞解除由C记录原因后回到PLANNED或IN_PROGRESS。集成失败回IN_PROGRESS并保留失败报告。STALE窗口仅在认领表标STALE，不假造任务已经失败/完成。已DONE发现缺陷，登记新修复slice、标相应版本门禁失效，修复后重新验收；保留之前证据，不改写历史报告。

worker只向自己的handoff目录写 `TASK_LOCAL_PASS` / `TASK_LOCAL_FAIL` / `BLOCKED`。C核实结果后更新共享状态。`DONE`必须是集成后的完成，不能仅是worker的本地测试成功。门禁状态只接受PENDING/ACCEPTED/REJECTED，ACCEPTED必须关联实际证据及对应基线hash。

## 4. 工作目录、基线与环境隔离

1. 先识别仓库是否有Git、HEAD、dirty/untracked文件、已有AGENTS及用户数据位置。保留用户未提交改动；任何一方不得 `reset --hard`、`clean -fd`、覆盖恢复用户文件或清卷。
2. 有Git且存在适用基线时，由C在授权范围创建独立worktree。仅创建工作区/分支不等于自动commit、merge或push获授权。无可用Git基线或包含必须共享的未提交实现时，用新目录复制代码快照并生成manifest；排除秘密、用户数据卷和历史目录。记录排除项，不能漏掉本任务依赖的未提交代码。
3. 所有worker使用同一基线manifest+contractRev；新增与修改文件逐一hash。C不得只把HEAD当基线，因为HEAD可能不含已授权的工作区变更。
4. 每个窗口独立Compose project name、容器网络、测试数据库/对象prefix、journal目录、应用端口。使用 `larder_<owner>_<runId>`，长度/字符按工具限制规范化。端口从C分配表领取，不随机抢默认端口。
5. 故障测试仅在带测试标记的隔离环境。测试脚本启动前打印并校验数据库名、卷名、对象prefix和绝对journal路径；无法证明隔离则停止该测试，写BLOCKED。不得将“不想装多套依赖”作为共用真实库做故障注入的理由。
6. 有共享开发依赖时只允许普通读写测试且每窗口隔离namespace；重启容器、改broker策略、停网络、删除对象、迁移升级、损坏journal等排他操作必须领取 `environment:<name>` 独占资源，并确认没有其他测试使用。用户真实数据仍不在授权内。

## 5. 文件所有权与锁

以下文件/资源默认C独占，不能由多个窗口“最后合并一下”：根README/AGENTS、tasks台账、contracts目录、全局错误码和配置清单、root Compose/CI、依赖锁、Flyway编号登记、frontend全局路由/设计tokens/Query keys/http封装、Runner公开run模型与journal格式。

路径重叠判定：两个规范化相对路径相等，或一个是另一个目录前缀，即冲突；不以字符串任意前缀判断（`tool`与`tools`不是同目录）。不允许`..`、绝对路径和通配符作为allowlist逃逸。大小写按Windows不敏感比较。明确文件路径锁仅锁该文件；目录路径锁包含后代。

资源锁覆盖路径之外的语义冲突，例如 `schema:job`、`contract:run-v1`、`frontend:design-system`、`migration-registry`、`environment:integration`。不同目录修改同一数据语义时仍冲突。worktree只能防止文件覆盖，不能消除契约冲突。

认领超时默认30分钟没有heartbeat即标STALE，**不能因此自动抢占**。C需确认旧worker已经停止写入或将其工作区封存为只读交接，再释放锁/换owner。保留旧产物；不杀进程、不删除目录来抢任务。人工窗口无自动心跳时，在工具完成或阶段汇报更新即可；C可延长长测试认领并记录。

## 6. 契约变更请求 CR

worker发现契约不足时，继续与此无关的工作，并向C交付：CR编号、现有行为、触发样例、希望修改的字段/状态/API、消费者、兼容性、迁移/回滚、增加测试、影响任务。不能偷偷在本地发明新字段后要求其他端迁就。

C处理步骤：识别是否核心范围变化→对正常兼容改动做技术决策→涉及用户已锁定核心目标的替换才提用户批准→暂停受影响slice派发→更新04、机器schema、样例、生成代码和错误表→跑兼容测试→生成新contractRev→发布迁移说明→消费者各自确认基线升级→恢复派工。无关任务继续。旧contractRev的实现进入集成前必须明确重放适配，不能用“都是v1”掩盖hash不同。

迁移由worker给草案，C分配唯一Flyway编号并放入公共迁移目录；主表/索引变更经SQL审查、真实MySQL空库与已有数据升级测试。已经应用的迁移只新增修复文件，不能改旧checksum。两个分支抢到相同编号时，尚未应用的文件可在C登记下重编号；已应用情况必须保留历史并设计前滚修复，不能清库重来。

## 7. 交接与集成顺序

worker交付 `handoff.json`、`changes.patch`（若可用）、`new-files/`、`file-manifest.json`、测试日志与summary。manifest逐文件含path、changeType、baseSha256（新增为null）、resultSha256、size；文件列表必须包含未跟踪新增文件。`git diff`不包含未跟踪文件，不能把一个空patch当交付完整。使用工具结构化参数或文件输出patch，避免PowerShell重定向编码破坏二进制。

集成顺序：核对任务依赖/锁/基线→检查范围与敏感信息→核对当前集成树baseSha→审阅更改→在集成树应用→再生成契约消费者（如适用）→跑任务测试及受影响边界→Q独立检查→记录新manifest→更新DONE→释放锁。若当前目标已改动，先生成明确冲突清单，不用worker整目录覆盖。超范围文件留在worker目录等待CR，不整包复制进去。

普通代码文件的审阅后集成属于已授权开发。Git commit/merge/push/tag或公开部署仍按已有用户授权执行；没有授权时保持可审查的工作区更改。不得把“集成”一词当自动Git merge授权。

失败隔离：C拒绝的是本次交接或部分文件，不删除worker产物；登记原因及恢复路径。若需要撤回已集成改动，先核对后续改动依赖，生成精确反向补丁并保留快照，不能reset整个仓库。用户原有重要文件遵守AGENTS保护要求。

## 8. 标准handoff字段

```json
{
  "taskId": "V08-T03", "sliceId": "V08-T03.BE",
  "result": "TASK_LOCAL_PASS",
  "baseSnapshot": "<sha256>", "contractRev": "<sha256>",
  "summary": "<具体行为变化与原因>",
  "changedFilesManifest": "file-manifest.json",
  "checks": [{"command": "<真实命令>", "exitCode": 0, "passed": 0, "failed": 0, "skipped": 0, "log": "<日志路径>"}],
  "acceptanceEvidence": {"A19": "<报告路径>"},
  "notRun": [], "knownLimitations": [], "newDependencies": [],
  "migrationNotes": "<迁移或N/A原因>", "contractChanges": [],
  "commentReview": {"publicSymbols": "<报告>", "sqlComments": "<报告或N/A>", "complexMechanisms": ["<六项说明与测试ID>"]},
  "nextIntegrationChecks": ["<集成后必须执行的检查>"],
  "locksToReleaseAfterIntegration": ["module:approval"]
}
```

示例中的passed=0不是通过证据。实际报告零用例、skip必需场景、缺依赖只能FAIL/BLOCKED；“没有发现问题”不是测试结果。不能声称全局发布就绪；由C结合整轮状态给出结论。

## 9. 不做什么

不共享一个可写checkout让多窗口自由改；不让Agent各自重构公共层；不凭heartbeat过期抢写；不绕过契约冻结；不自动清环境；不把本地通过冒充集成完成；不把生成代码手工改成和schema不一致。
