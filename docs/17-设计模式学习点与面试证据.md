# 17 设计模式、学习点与面试证据

执行对象：实现Agent和最终证据整理Agent。模式是具体问题的解法，不是要求堆出一份GoF全集。下面将实现边界、替代方案、失败风险、测试和面试追问绑定；只有真实源码和实验存在后才写成已完成亮点。

## 1. 使用矩阵

| 模式/机制 | 使用位置与接口 | 为什么需要 | 防过度设计与验证 |
|---|---|---|---|
| Strategy 策略 | `RetrievalStrategy`关键词/语义；`ReviewScheduler`固定sm2版本；Runner不同source extractor | 同一输入/输出合同存在真实不同算法，便于对照与演进 | 无需每个if都拆策略；使用同一fixture合同测试，固定算法版本 |
| Adapter 适配器 | `ObjectStore` S3适配、`RunnerClient` HTTP、`ModelProvider`供应商差异 | 将厂商返回/错误/流式语义转换为内部稳定模型 | 不做万能云平台；测试超时、格式变化、UNKNOWN和能力不支持 |
| Registry + Factory | ToolRegistry按toolName解析已注册handler；ExtractorRegistry按输入类型选择 | 新工具/来源不需要修改巨大switch，且能集中校验重名/schema | 注册白名单，不通过反射加载用户任意类；启动时重复名失败 |
| Command 命令 | `CreateItemCommand`、`ApplyProposalCommand`、review request；tool proposal | 将意图、身份、版本和幂等条件显式封装，便于审计/重放请求结果 | Command不等于任意执行对象；审批必须绑定hash，不能重放外部副作用 |
| Application Service / Facade | ContentApplicationService、ApprovalApplicationService | 给controller/tool提供明确用例入口和事务边界 | Facade不可膨胀成上千行万能服务；domain算法/I/O拆开 |
| Repository/Port | LeaseRepository、GenerationRepository、MemoryRepository | 将关键条件更新和锁语义集中，测试清楚；隔离domain与MyBatis | 只包装有领域含义操作，不机械在Mapper上再复制所有CRUD方法 |
| State machine | Job/Run/Approval/Memory；枚举+转移表+guard | 非法转移、取消竞争和恢复可验证 | 首版不用状态模式为每个状态建类；复杂到确有差异才拆handler |
| Pipeline / Chain | 提取→分段→结构化→引用校验；授权→schema→scope→预算→执行 | 每阶段输入输出与失败原因可审查 | 顺序固定、阶段有名；禁止深层链式DSL隐藏事务与外部调用 |
| Decorator / Interceptor | 外部client tracing/限流；工具调用度量 | 横切行为统一，避免每工具复制代码 | 重试不能无脑装饰所有调用；未知副作用不得自动重发；装饰顺序有测试 |
| Observer / Event | 提交业务后Outbox通知索引/worker，SSE展示状态 | 解耦后台处理与页面通知 | Spring内存事件不能代替持久Outbox；事件重复/乱序测试必需 |
| Snapshot + Replay | JSONL事实与Checkpoint；压缩context提交 | 降低恢复成本同时保持可追溯事实 | 不把Checkpoint当第二权威，不存隐藏思维，不静默改日志 |
| Builder（有限使用） | 完整模型请求包含system/tool/memory/evidence/budget时的构造 | 让请求所有部分在预算与hash之前完整汇总 | 简单三字段DTO不必Builder；构造后不可变，测试漏算tool schema |

Outbox、Inbox、lease fencing、CAS、RRF不是GoF设计模式；它们分别属于可靠消息/并发控制/检索算法。面试描述要正确分类，不能把所有技术都叫“用了设计模式”。不默认引入抽象工厂、访问者、复杂继承模板方法或完整CQRS框架；只在真实需求证明后决定。

## 2. 三个完整实现案例

### 案例A：检索策略与融合

`SearchApplicationService`校验query/scope→调用KeywordRetriever与SemanticRetriever→在统一Candidate类型上做RrfFusion→AuthoritativeFilter→按item聚合/稳定排序→CursorPage。Keyword与Semantic策略只返回候选，不直接决定用户可见；权限复核是强制公共步骤，新增策略也不能绕过。

Candidate至少包含itemId/revisionId/chunkId/generationId/route/rank/profileId；原始分数只用于诊断，不跨算法直接相加。RRF纯函数用人工可计算数据测重复chunk、缺一路、并列、权重与k。优化对照固定query/qrels，允许最终发现某策略没有收益。面试可问：为何不直接加余弦与关键词分数？为什么过滤后不足K？为什么在向量库加owner过滤还要复核？

### 案例B：工具注册、策略验证与审批命令

`ToolDefinition`声明name/version/schema/read-or-propose/scope/timeout/resultLimit；`ToolRegistry`拒绝重复注册；`ToolExecutor`先做参数/范围/预算验证，再有界调度handler。只读handler可并发；写动作handler只形成Proposal，实际Java ApplyProposalCommand要求有效审批和actionId。

横切trace装饰器只记录安全元信息；retry decorator只用于明确幂等读，不能包在apply未知结果外自动再创建新action。大结果治理统一截断摘要+artifact引用，不让每handler随意吞文本。测试用故意乱序与重复call、目标变更、超时、审批过期证明约束。面试可问：为什么“模型已经解释理由”仍不代表批准？工具结果如何配对？为什么actionId不能和callId混用？

### 案例C：版本化复习策略与翻卡

`ReviewScheduler`接受旧ReviewState、grade、Clock/时区规则、schedulerVersion，返回新状态，不写库。`ReviewApplicationService`负责锁、幂等、权限与日志；前端FlipCard只控制question/answer显示，不计算权威due。将来新增算法只新增version策略，新旧review_log仍能解释，不把全部历史按新算法静默重算。

问答/挖空采用翻面，背诵/时间戳展开，是展示策略，不要为了这四种UI写一个全局插件框架。评分要等服务端确认；动画结束只是允许显示按钮，不构成复习已提交。测试固定时间与给定状态，覆盖重来、首次/第二次成功、ease最低值、旧stateVersion、重复requestId。面试可问：为什么评分和翻面是两个状态机？刷新后重复点击如何避免多算？时区变化是否重写历史统计？

## 3. 学习与面试问题树

| 模块 | 基础问题 | 深挖问题 | 必须准备的证据 |
|---|---|---|---|
| MySQL | 索引/唯一约束/事务隔离/MVCC | 范围锁、死锁、复合索引左前缀、SKIP LOCKED局限、跨owner FK | DDL、EXPLAIN、两事务时间线、死锁/恢复日志 |
| Redis | 缓存与限流、TTL | 热点/穿透/雪崩、单飞、profile版本key、故障降级、为什么不能最终锁 | L03对照和业务最终条件SQL |
| RabbitMQ | exchange/queue/confirm/ack | confirm丢失、unroutable、持久接管、DLQ、重复消费、quorum实验 | A02–A07、L04原始broker与DB记录 |
| 对象存储 | bucket/key/version/multipart | ETag与SHA、孤立对象、DB引用与对象发布顺序、恢复一致性 | 产物manifest、失败注入、L05 |
| 索引 | 分段/关键词/向量/融合 | 原子指针、旧索引复核、迟到覆盖、candidate与ranking miss | generation表、任务状态、query级评测 |
| Agent运行 | 工具调用/模型call/会话 | 日志fsync、尾写/中段损坏、checkpoint提交、UNKNOWN外部效果 | 崩溃前后文件hash与重放trace |
| 审批 | scope/权限/幂等 | TOCTOU、payloadHash、版本绑定、响应丢失、一次DB效果边界 | A19/A20数据库前后与action结果 |
| 记忆 | 显式写入、召回、替代撤销 | 旧context复活、每call授权线性化、在途请求边界 | A21/A22实际授权/请求证据 |
| 压缩 | token预算、摘要 | 完整请求预算、事实快照与summary差异、原子context提交、质量退化 | token前后+独立Verifier，不只一张节省图 |
| 前端 | Query缓存、状态、响应式 | SSE去重/snapshot、未知写结果、审批diff、翻面焦点/减少动画 | 真E2E、状态覆盖表、浏览器截图 |
| 工程化 | CI/迁移/可观测 | 测试发现为零、Mock漏检、升级恢复、敏感信息和指标基数 | CI报告、L06–L08、全新目录恢复 |

## 5. 不做什么

不为面试强塞无业务价值的类层次；不写“精通23种设计模式”；不把未跑的实验当经验；不说消息/模型绝对exactly-once；不把参考简历成绩改个项目名照抄。
